## 2.1 Архітектура та загальний принцип роботи системи

Система Serverscope побудована за принципом розподілу відповідальності між трьома незалежними компонентами: фоновим Worker-процесом, серверним застосунком Backend та реляційною базою даних PostgreSQL. Кожен компонент має чітко визначену роль і не виходить за її межі. Це дозволяє масштабувати, замінювати або перезапускати будь-який компонент незалежно від інших.

**Worker** ніколи не отримує HTTP-запити та не взаємодіє з клієнтами — він лише пише дані до бази. **Backend** ніколи не звертається до Steam API — він лише читає вже зібрані дані. Вся бізнес-логіка збору, обрахунку рейтингів та агрегації зосереджена виключно у Worker.

**Таблиця 2.1 — Компоненти системи Serverscope**

| Компонент    | Технологія                            | Відповідальність                                              |
|--------------|---------------------------------------|---------------------------------------------------------------|
| Worker       | Node.js, TypeScript, TypeORM, node-cron | Збір даних з Steam API, розрахунок рейтингів, очищення БД   |
| Backend      | NestJS, TypeScript, TypeORM           | REST API, пошук, фільтрація, видача графіків                  |
| Database     | PostgreSQL                            | Спільне сховище; 4 таблиці: servers, online_records, server_rankings, games |
| Frontend     | React / Next.js                       | Веб-інтерфейс; споживає Backend API                          |

### 2.2.1 Отримання та оновлення інформації про сервери

Збір даних здійснюється Worker-процесом кожні 15 хвилин шляхом звернення до Steam Web API. Для отримання переліку серверів використовується метод `IGameServersService/GetServerList` з параметрами: API-ключ автентифікації, фільтр за ідентифікатором гри (`\appid\{id}\empty\1`) та ліміт 10 000 записів.

**Механізм upsert.** Для уникнення дублювання серверів при повторному зборі застосовується операція `INSERT ... ON CONFLICT (ip, query_port) DO UPDATE`. Пара (ip, query_port) є унікальним ідентифікатором сервера. При знаходженні вже існуючого запису оновлюються поточний стан (players, map, version, is_online) та час останнього виявлення. Такий підхід є атомарним і не потребує попереднього SELECT-запиту, що усуває ризик гонки процесів.

### 2.2.2 Аналіз та індексація даних

При досягненні таблицею `online_records` понад двох мільярдів рядків, а `servers` — понад 600 000 записів, без належної індексації PostgreSQL виконує повне сканування таблиці (Sequential Scan). Для таблиці `online_records` це означає перебір мільярдів рядків при кожному запиті — час виконання перевищував десятки секунд, що є неприйнятним для API реального часу.

Після аналізу планів виконання запитів за допомогою команди `EXPLAIN ANALYZE` були визначені та додані складові індекси. Складовий (composite) індекс дозволяє PostgreSQL задовольнити запит з кількома умовами фільтрації (WHERE + ORDER BY) звернувшись лише до індексних сторінок, оминаючи читання основних даних таблиці (Index-Only Scan).

**Таблиця 2.3 — Індекси бази даних Serverscope**

| Індекс                                          | Таблиця          | Поля                          | Прискорює                                               |
|-------------------------------------------------|------------------|-------------------------------|----------------------------------------------------------|
| `idx_servers_appid_rank`                        | servers          | (appid, rank)                 | Пагінований список серверів гри, відсортований за рейтингом |
| `idx_online_records_server_id_recorded_at`      | online_records   | (server_id, recorded_at) UNIQ | Запити графіків онлайну за часовим діапазоном            |
| `idx_online_records_recorded_at`                | online_records   | (recorded_at)                 | Задача очищення: downsampling та видалення старих записів |
| `idx_server_rankings_server_id_calculated_at`   | server_rankings  | (server_id, calculated_at) UNIQ | Отримання найактуальнішого рейтингу сервера            |
| `idx_server_rankings_appid_calculated_at_rank`  | server_rankings  | (appid, calculated_at, rank)  | Щоденне ранжування: сортування серверів гри за поточну добу |

**Таблиця 2.4 — Продуктивність запитів до та після індексації**

| Запит                                              | Без індексу       | З індексом     | Покращення   |
|----------------------------------------------------|-------------------|----------------|--------------|
| Список серверів гри, сортування за rank (пагінація)| ~8–15 с           | < 50 мс        | > 200×       |

### 2.2.3 Збереження статистичної інформації

Система використовує дворівневу модель зберігання статистики: деталізовані записи для короткострокового аналізу та агреговані — для довгострокового.

**Таблиця online_records** накопичує запис кожні 15 хвилин для кожного активного сервера. При обсязі понад 2 мільярди рядків зберігання повної деталізації без обмежень призвело б до неконтрольованого зростання бази даних. Тому щодоби виконується процедура Downsampling: записи старші за 24 години замінюються одним усередненим погодинним записом. Записи старші 30 днів видаляються повністю.

**Поле `hourly_online` (JSONB)** в таблицях `servers` та `games` є денормалізованим кешем: масив із 24 числових значень, що зберігає середній онлайн за кожну з останніх 24 годин. Це дозволяє відобразити погодинний графік для будь-якого сервера або гри без виконання JOIN-запиту до `online_records` — дані вже готові у самому записі.

**Таблиця server_rankings** зберігає щоденні знімки рейтингу — по одному запису на сервер на добу. Записи не перезаписуються, оскільки це дозволяє будувати графік динаміки рангу та score у часі.

**Таблиця 2.5 — Характеристики зберігання сутностей системи**

| Таблиця          | Рядків         | Крок оновлення  | Retention           | Призначення                         |
|------------------|----------------|-----------------|---------------------|-------------------------------------|
| servers          | ~600 000       | 15 хвилин       | Безстроково         | Актуальний стан усіх серверів       |
| online_records   | > 2 000 000 000| 15 хвилин       | 0–24 год деталі, 24 год–30 днів агрегат, потім видалення | Часовий ряд онлайну |
| server_rankings  | ~600 000/добу  | 1 раз на добу   | Безстроково         | Щоденні знімки рейтингів            |
| games            | 15             | 1 раз на годину | Безстроково         | Поточна статистика та графіки ігор  |

## 2.3 Пошук, фільтрація та рейтингова система серверів

Backend надає REST API з гнучкими параметрами пошуку та фільтрації. Основний ендпоінт `GET /servers` приймає набір необов'язкових параметрів, описаних у таблиці 2.6.

**Таблиця 2.6 — Параметри фільтрації API `/servers`**

| Параметр     | Тип     | Опис                                              | Значення за замовч. |
|--------------|---------|---------------------------------------------------|---------------------|
| `appid`      | int     | Ідентифікатор гри (обов'язковий)                  | —                   |
| `search`     | string  | Пошук за назвою (регістронезалежний)              | —                   |
| `ip`         | string  | Точний збіг IP-адреси                             | —                   |
| `map`        | string  | Точний збіг назви карти                           | —                   |
| `isSecure`   | boolean | Фільтр за наявністю VAC-захисту                   | —                   |
| `isOnline`   | boolean | Фільтр за статусом онлайн                         | —                   |
| `sortBy`     | enum    | Поле сортування: rank \| players \| name          | `rank`              |
| `sortOrder`  | enum    | Напрямок: asc \| desc                             | `asc`               |
| `page`       | int     | Номер сторінки (мінімум 1)                        | `1`                 |
| `limit`      | int     | Записів на сторінку (максимум 100)                | `25`                |

**Підхід до пошуку.** При розробці були розглянуті три методи текстового пошуку за назвою сервера. Назви серверів у Steam-спільноті мають специфічний формат: вони містять теги, скорочення, спецсимволи та цифри (наприклад: `[UA] DayZ | PvP | x5 | Loot+`). Це суттєво впливає на вибір методу.

**Таблиця 2.7 — Порівняння методів текстового пошуку**

| Метод               | Індекс | Мін. довжина запиту | Ефективність для серверних назв | Складність |
|---------------------|--------|---------------------|----------------------------------|------------|
| `ILIKE '%query%'`   | Немає  | 1 символ            | Висока — знаходить підрядок      | Низька     |
| `pg_trgm` (GIN)     | GIN    | 3 символи           | Низька — теги/цифри розбивають тригреми | Середня |
| PostgreSQL Full-Text Search | GIN | Слова  | Неприйнятна — серверні назви не є природною мовою | Висока |

Тригремний пошук (`pg_trgm`) був протестований із GIN-індексом: при пошуку коротких рядків (1–2 символи) він не спрацьовує, а для серверних назв зі спецсимволами, цифрами та тегами тригреми не дають переваги перед `ILIKE`. Метод `ILIKE '%query%'` обраний як оптимальний: він підтримує пошук від першого символу, коректно обробляє будь-які підрядки та є достатнім для обсягу даної задачі.

**Відображення рейтингу.** При видачі списку серверів поля `popularity` та `stability` додаються до кожного запису через окремий запит із використанням `DISTINCT ON (server_id) ORDER BY calculated_at DESC` — це забезпечує завжди актуальні показники з останнього розрахунку. Сервери з `rank = 0` (ще не отримали рейтинг) виводяться в кінці списку незалежно від напряму сортування.
