### 1.4 — Математична модель оцінки активності та популярності серверів

**Що потрібно описати:**
Математична модель рейтингу серверів — формули, обґрунтування вагових коефіцієнтів.

**Формула рейтингу (з коду rankingService.ts):**

$$\text{score}_i = 0.5 \cdot \frac{M_i}{M_{max}} + 0.25 \cdot \left(1 - \frac{E_i}{96}\right) + 0.25 \cdot P_i$$

**Компоненти:**
- $M_i$ — медіана онлайну сервера $i$ за останні 24 год (по погодинним бакетам, заповненим нулями якщо даних немає)
- $M_{max}$ — максимальна медіана серед усіх серверів цієї гри в розрахунковий день (нормалізація всередині гри, ∈ [0,1])
- $E_i$ — `empty_count`: кількість 15-хвилинних записів з `players = 0` за останні 24 год. Максимум = 96 (24г × 4 записи/год)
- $1 - E_i/96$ — uptime ratio: частка часу коли сервер не був порожнім (∈ [0,1])
- $P_i$ — `historical_rank_avg`: нормалізований середній ранг за останні 3 дні

**Формула $P_i$ (historical rank avg):**

$$P_i = \frac{1}{K} \sum_{k=1}^{K} \left(1 - \frac{r_{t-k,i} - 1}{N_{t-k} - 1}\right)$$

де $r_{t-k,i}$ — місце сервера $k$ днів тому, $N_{t-k}$ — всього серверів у той день. Значення ∈ [0,1], де 1 = перше місце. Для нових серверів без історії = 0.5 (нейтральне).

**Показники popularity та stability (з коду):**
- `popularity` = відносна позиція у рейтингу (нормалізований ранг * загальна кількість серверів)
- `stability` = uptime_ratio з останнього запису рейтингу

**Що включити:**
- Обидві формули в LaTeX/KaTeX
- Таблицю компонентів рейтингу (компонент / вага / що вимірює)
- Обґрунтування вагових коефіцієнтів (чому 50/25/25)
- Приклад розрахунку для умовного сервера
- ASCII або текстову схему алгоритму розрахунку

**ПРОМПТ:**

```

Контекст: система Serverscope щодоби розраховує рейтинги для всіх серверів кожної гри.

Формула рейтингового балу:

  score_i = 0.5 * (M_i / M_max) + 0.25 * (1 - E_i/96) + 0.25 * P_i

де:
- M_i — медіана онлайну сервера i за останні 24 год (погодинні бакети, пропуски = 0)
- M_max — максимальна медіана серед усіх серверів тієї ж гри в цей день (нормалізатор, ∈ [0,1])
- E_i — кількість 15-хв записів з players=0 за 24 год (empty_count, максимум = 96)

Нові сервери без історії отримують P_i = 0.5 (нейтральне значення).

Додатково: popularity = нормалізований ранг помножений на загальну кількість серверів; stability = uptime_ratio.

Обов'язково включи:

### 2.1 — Архітектура та загальний принцип роботи системи

**Що описати:**
Загальна архітектура трикомпонентної системи: Worker → PostgreSQL ← Backend → Frontend.

**Компоненти:**
- **Worker** (Node.js/TypeScript): фоновий процес, збирає дані, розраховує рейтинги, очищає БД
- **Backend** (NestJS/TypeScript): REST API, отримує дані з БД, надає клієнту
- **Database** (PostgreSQL): спільне сховище, 4 таблиці
- **Frontend** (React/Next.js — окремий репозиторій): веб-інтерфейс

**Принцип розділення відповідальності:**
- Worker ніколи не отримує HTTP-запити — тільки пише в БД
- Backend ніколи не звертається до Steam API — тільки читає з БД
- Вся бізнес-логіка розрахунків — у Worker

**Що включити:**
- ASCII-діаграму архітектури (компоненти + стрілки + технології)
- Таблицю: компонент / технологія / відповідальність
- Коротко про кожен компонент

### 2.2.2 — Аналіз та індексація даних

**Що описати:**
Проблема продуктивності при великих обсягах даних і вирішення через індекси.

**Ключова "драматична" частина:**
> Спочатку індексів не було. При 2+ мільярдах записів в `online_records` та 600k+ в `servers` — запити виконувались десятки секунд (full table scan). Після аналізу планів виконання запитів (EXPLAIN ANALYZE) були додані складові індекси.

**Існуючі індекси (з коду):**
| Таблиця | Індекс | Поля |
|---|---|---|
| servers | idx_servers_appid_rank | (appid, rank) |
| online_records | idx_online_records_server_id_recorded_at | (server_id, recorded_at) — UNIQUE |
| online_records | idx_online_records_recorded_at | (recorded_at) |
| server_rankings | idx_server_rankings_server_id_calculated_at | (server_id, calculated_at) — UNIQUE |
| server_rankings | idx_server_rankings_appid_calculated_at_rank | (appid, calculated_at, rank) |

**Що включити:**
- Таблицю індексів з поясненням для чого кожен
- ASCII-схему "до індексів" vs "після": час запиту
- Пояснення чому складові індекси (composite) ефективніші для наших запитів

**ПРОМПТ:**

```
Напиши підрозділ 2.2.2 "Аналіз та індексація даних" для університетського звіту.

Контекст: система Serverscope зберігає понад 600 000 серверів і понад 2 мільярди записів онлайну.

Ситуація: на початку розробки індексів не було. Через великий обсяг даних запити до таблиці online_records та server_rankings виконувались дуже повільно (PostgreSQL виконував full sequential scan). Після аналізу планів виконання запитів (EXPLAIN ANALYZE) були визначені та додані необхідні індекси.

Індекси що були додані:

Таблиця servers:

### 2.2.3 — Збереження статистичної інформації

### 2.3 — Пошук, фільтрація та рейтингова система серверів

**Що описати:**
Механізми пошуку і фільтрації в бекенді + як рейтинг застосовується при видачі.

**Пошук — важливо розповісти:**
1. **Поточний підхід**: `ILIKE '%search%'` — регістронезалежний substring пошук
2. **Тригрем пошук (pg_trgm)**: спробували `GIN`-індекс з `%`-подібністю — не дало очікуваного результату, бо назви серверів містять специфічні символи, цифри, теги (`[RU] DayZ | PvP | x5`), де тригреми не мають переваги над ILIKE
3. Висновок: для коротких пошукових рядків (менше 3 символів характерно для ігрових серверів) ILIKE достатньо

**Фільтри (з QueryServersDto):**
- appid (обов'язковий)
- search (ILIKE по name)
- ip (точний збіг)
- map (точний збіг)
- isSecure (boolean)
- isOnline (boolean)
- sortBy: rank | players | name
- sortOrder: asc | desc
- page, limit (пагінація, max 100)

**Рейтинг при видачі:**
- Сортування за `rank` (0 = без рейтингу, виводяться останніми)
- `popularity` та `stability` — приєднуються з останнього запису server_rankings через DISTINCT ON

### 4.2 — Порівняння ефективності використаних рішень

**Що описати:**

Контекст: система Serverscope, PostgreSQL, 600k+ серверів, 2+ млрд записів онлайну.

Порівняй ефективність наступних рішень:

1. ІНДЕКСИ — до і після:
   Запит: "отримати графік онлайну сервера за 7 днів" (JOIN online_records за server_id + recorded_at)
   - Без індексу: sequential scan таблиці 2 млрд рядків → час ≈ 30–60 с
   - З індексом idx_online_records_server_id_recorded_at: index scan → < 100 мс

2. ДЕНОРМАЛІЗАЦІЯ hourly_online (JSONB):
   - Без JSONB: JOIN + GROUP BY + AVG за 24 год для кожного API-запиту → ~500 мс
   - З JSONB кешем: просте читання одного поля → < 10 мс

3. DOWNSAMPLING:
   - Без downsampling після 30 днів: таблиця зростала б до ~20 млрд рядків
   - З downsampling: стабілізація на ~2 млрд рядків

4. UPSERT vs INSERT+SELECT:
   - INSERT+SELECT: 2 запити + можливий race condition
   - ON CONFLICT DO UPDATE: 1 атомарний запит

Включи:
- Зведену таблицю порівняння (рішення / без оптимізації / з оптимізацією / покращення)
- ASCII-графік або таблицю: зростання об'єму online_records в часі (з cleanup vs без)

Стиль: аналітичний, академічний, українська мова. Markdown. Обсяг: 600–800 слів.
