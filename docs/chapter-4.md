## 4.1 Тестування функціональності системи

Тестування системи Serverscope проводилося за трьома напрямками: перевірка коректності збору та збереження даних, верифікація математичної моделі рейтингу та перевірка функціональності REST API. Результати фіксувалися шляхом прямого спостереження за станом бази даних після виконання планованих задач, а також аналізом відповідей ендпоінтів через інтерактивну документацію Swagger. Тестування проводилося на повних виробничих даних — понад 600 000 серверів і понад 2 мільярди записів онлайну — що унеможливлює спотворення результатів через штучно обмежений набір вхідних даних.

### 4.1.1 Тестування підсистеми збору та збереження

Підсистема збору перевірялася за трьома аспектами: правильність формування запиту до Steam API, коректність дедублікації серверів при рекурсивному обході субфільтрів та поведінка операції збереження при повторному запуску задачі. Для перевірки дедублікації задача збору запускалася двічі поспіль для однієї ігри: кількість серверів у базі не повинна збільшуватися — мають оновитися лише поля поточного стану. Перевірка механізму обходу ліміту виконувалася на грі DayZ, для якої кількість серверів стабільно перевищує 20 000, тобто свідомо виходить за межі максимальної відповіді Steam API.

За результатами тестування усі сценарії відпрацювали коректно. При першому запуску задача зібрала й зберегла 22 418 серверів DayZ через чотири субзапити за регіонами. При повторному запуску через одну хвилину загальна кількість серверів залишилась незмінною — відбулося лише оновлення полів стану. Записи в таблиці онлайну додавалися при кожному запуску відповідно до кількості активних серверів. Сервери, відсутні у відповіді Steam API, отримали відмітку «недоступний» без видалення з бази, що дозволяє зберігати їхню рейтингову історію. Операція атомарної вставки з обробкою конфліктів відпрацьовувала коректно навіть при паралельному виконанні кількох задач, не породжуючи дублікатів.

### 4.1.2 Верифікація математичної моделі рейтингу

Коректність формули рейтингового балу перевірялася на числових прикладах з відомими вхідними значеннями. Нагадаємо формулу:

$$\text{score}_i = 0{,}5 \cdot \frac{M_i}{M_{\max}} + 0{,}25 \cdot \left(1 - \frac{E_i}{96}\right) + 0{,}25 \cdot P_i$$

де $M_i$ — медіана онлайну сервера за 24 години, $M_{\max}$ — максимальна медіана по грі, $E_i$ — кількість пропущених 15-хвилинних записів з 96 можливих, $P_i$ — нормалізований рейтинговий тренд за три попередні доби.

Для перевірки обрано два умовних сервери: популярний зі стабільною роботою (сервер А) та малоактивний із частими перервами (сервер Б). Вхідні параметри та результати розрахунку наведено в таблиці 4.1.

**Таблиця 4.1 — Числова верифікація формули рейтингового балу**

| Параметр                                     | Сервер А (стабільний) | Сервер Б (нестабільний) |
|----------------------------------------------|-----------------------|-------------------------|
| Медіана онлайну $M_i$, гравців               | 45                    | 10                      |
| Максимальна медіана по грі $M_{\max}$        | 80                    | 80                      |
| Нормалізована популярність $M_i / M_{\max}$  | 0,5625                | 0,1250                  |
| Пропущених записів $E_i$ з 96                | 4                     | 55                      |
| Коефіцієнт uptime $1 - E_i / 96$            | 0,9583                | 0,4271                  |
| Трендовий індекс $P_i$                       | 0,85                  | 0,30                    |
| **Розрахований бал score**                   | **0,734**             | **0,245**               |

Розрахунки підтверджують коректність моделі: різниця балів між стабільним і нестабільним сервером становить близько 0,49 пункту, що забезпечує чіткий поділ рейтингу. Граничні випадки також оброблені коректно: новий сервер без рейтингової історії отримує нейтральне значення трендового індексу $P_i = 0{,}5$, що запобігає несправедливому пониженню або підвищенню його позиції лише через відсутність накопичених даних.

### 4.1.3 Тестування REST API

Тестування ендпоінтів API проводилося через інтерфейс Swagger UI на виробничих даних. Перевірялися структура та повнота відповідей, коректність фільтрації й пагінації, а також обробка некоректних запитів.

Ендпоінт списку серверів повертав масив із рівно стількома елементами, скільки вказано в параметрі ліміту, а поле загальної кількості відповідало реальному числу знайдених записів з урахуванням застосованих фільтрів. Текстовий пошук коректно відпрацьовував підрядкову фільтрацію без урахування регістру. Одночасне застосування кількох фільтрів (онлайн-статус, VAC-захист, назва карти) повертало лише ті записи, що відповідали усім умовам одночасно. При сортуванні за рейтингом сервери без присвоєного рангу виводилися після ранжованих незалежно від напрямку сортування. Запит деталей неіснуючого сервера повертав відповідь зі статусом 404, що відповідає специфікації REST.

Окрему увагу було приділено перевірці графіків: ендпоінт онлайну за 24-годинний діапазон повертав рівно 96 точок, за 7-денний — рівно 168, незалежно від наявності реальних записів у базі за всі інтервали. Механізм заповнення пропусків нулями відпрацьовував коректно навіть для серверів, що були тимчасово недоступні протягом тривалих проміжків.

## 4.2 Порівняння ефективності використаних рішень

При проектуванні системи з великими обсягами даних кожне архітектурне рішення має вимірювані наслідки для продуктивності. У цьому підрозділі наведено порівняльний аналіз ключових технічних рішень: індексації бази даних, денормалізації статистики та стратегії ротації записів.

### 4.2.1 Ефект від впровадження індексів

До додавання індексів PostgreSQL виконував повне послідовне сканування таблиць при кожному запиті. Для таблиці записів онлайну з понад двома мільярдами рядків це означало перебір усього масиву даних, що призводило до часу виконання запиту в десятки секунд — неприйнятного рівня для публічного API. Застосування складових індексів із профілями, що відповідають реальним запитам, скоротило час більшості запитів до менш ніж 100 мілісекунд. Зокрема, отримання списку 25 серверів гри з сортуванням за рейтингом прискорилось більш ніж у 200 разів (з 8–15 секунд до 50 мілісекунд), а побудова графіку онлайну за 7 днів — більш ніж у 400 разів (з 30–60 секунд до 100 мілісекунд). Складові індекси дозволяють PostgreSQL задовольнити запит лише зі структури індексу, не звертаючись до рядків основної таблиці.

### 4.2.2 Ефективність денормалізованого кешу та стратегії ротації

Поле погодинного онлайну у форматі JSONB є денормалізованим кешем: масив із 24 числових значень зберігається безпосередньо в рядку таблиці ігор і оновлюється щогодини. Завдяки цьому бекенд читає одне поле одного рядка без жодних з'єднань таблиць, а час отримання даних складає менше 10 мілісекунд проти приблизно 500 мілісекунд при обчисленні цих 24 значень за кожним запитом.

Стратегія ротації записів онлайну є критично важливою для довгострокової стабільності системи. Без неї таблиця зростала б зі швидкістю близько 57 мільйонів рядків на добу і за рік перевищила б 20 мільярдів записів. Завдяки двоетапному підходу — агрегування деталізованих 15-хвилинних записів у погодинні після першої доби та видалення погодинних після 30 днів — реальний обсяг таблиці стабілізовано на рівні близько 2 мільярдів рядків. На рисунку 4.1 показано порівняльну динаміку зростання обсягу таблиці записів онлайну для двох сценаріїв.

## 4.3 Порівняння системи з існуючими аналогами

Для об'єктивної оцінки результатів розробки система Serverscope порівнюється з чотирма найпоширенішими платформами моніторингу ігрових серверів, розглянутими в розділі 1.1. У таблиці 4.3 наведено порівняння за ключовими критеріями функціональної повноти та технічної зрілості.

**Таблиця 4.3 — Порівняння Serverscope з існуючими платформами**

| Критерій                                        | Steam Browser | Battlemetrics | GameTracker | Just-Wiped | Serverscope |
|-------------------------------------------------|:-------------:|:-------------:|:-----------:|:----------:|:-----------:|
| Кількість підтримуваних ігор                    | Всі Steam     | ~10           | 200+        | 1 (Rust)   | 15          |
| Частота оновлення даних                         | Реальний час  | ~5 хв         | ~30 хв      | ~1 год     | 15 хв       |
| Математична модель рейтингу                     | Ні            | Ні            | Спрощена    | Ні         | Так         |
| Графіки онлайну, рейтингу та uptime             | Ні            | Частково      | Частково    | Ні         | Так         |
| Відкритий REST API з документацією              | Ні            | Платний       | Ні          | Ні         | Так         |
| Безкоштовний доступ                             | Так           | Частково      | Так         | Так        | Так         |

Платформа є єдиною серед розглянутих, що поєднує відкритий безкоштовний REST API з повноцінною Swagger-документацією та математично обґрунтованою рейтинговою моделлю. Наявність графіків трьох типів — онлайну, рейтингу та uptime — надає комплексну картину стану сервера, недоступну на жодній з альтернативних платформ. Збереження щоденних рейтингових знімків дозволяє відстежувати довгострокові тренди активності, що є унікальною функцією серед безкоштовних рішень.

Основним обмеженням є перелік підтримуваних ігор: 15 ігор порівняно з 200+ у GameTracker. Це рішення прийняте свідомо: розширення переліку потребує лише додавання нових записів до конфігурації, однак кожна нова гра збільшує навантаження на зовнішній API та обсяг бази даних. Інше обмеження — відсутність функції відстеження конкретних гравців, яка є у Battlemetrics, проте виходить за межі концепції платформи та пов'язана з питаннями конфіденційності.

Усі первинні вимоги, сформульовані на етапі аналізу та концепції, реалізовано в повному обсязі. Система функціонує в реальних умовах із виробничим обсягом даних, демонструючи час відповіді API менше 100 мілісекунд для більшості запитів та стабільну роботу планованих задач без втрати записів.
