# РОЗДІЛ 3 — РЕАЛІЗАЦІЯ СИСТЕМИ SERVERSCOPE

---

## 3.1 Реалізація системи збору статистики

Worker-сервіс реалізований як автономний фоновий процес на Node.js з TypeScript. Він не має зовнішнього HTTP-інтерфейсу та взаємодіє виключно з базою даних PostgreSQL через бібліотеку TypeORM. Кодова база організована за принципом розподілу обов'язків: точка входу ініціалізує підключення до бази даних і реєструє планові задачі; рівень конфігурації описує підключення та перелік п'ятнадцяти відстежуваних ігор; рівень сутностей містить TypeORM-описи чотирьох таблиць; рівень задач включає чотири незалежні модулі; рівень сервісів реалізує логіку збереження та розрахунку рейтингів.

При запуску Worker спочатку встановлює з'єднання з базою даних, і лише після його підтвердження реєструються планові задачі. Якщо підключення не вдалося — процес завершується примусово, щоб системний менеджер (Docker або PM2) автоматично перезапустив сервіс. Такий підхід виключає виконання задач без активного з'єднання з базою.

У таблиці 3.1 наведено розклад усіх планових задач Worker-сервісу.

**Таблиця 3.1 — Розклад планових задач Worker-сервісу**

| Задача                    | Частота          | Призначення                                              |
|---------------------------|------------------|----------------------------------------------------------|
| Збір серверів             | Кожні 15 хвилин  | Запит до Steam API, збереження серверів та запис онлайну |
| Оновлення статистики ігор | Щогодини (UTC)   | Агрегування погодинного онлайну в таблицю ігор           |
| Розрахунок рейтингів      | Щодоби 00:00 UTC | Обчислення рейтингового балу та рангу для кожного сервера|
| Очищення даних            | Щодоби 12:00 UTC | Агрегування деталізованих записів та видалення застарілих|

Задача збору серверів є найскладнішою за логікою виконання. Вона послідовно обробляє всі п'ятнадцять ігор: для кожної формується запит до Steam Web API, дані нормалізуються та зберігаються. Ключова особливість — обробка ліміту API: якщо відповідь містить рівно десять тисяч серверів, запит розбивається на вужчі субзапити за регіоном або кількістю гравців із паузою в одну секунду між ними. Результати об'єднуються з усуненням дублікатів. На рисунку 3.1 наведено алгоритм виконання задачі.

**Рисунок 3.1 — Алгоритм задачі збору серверів**

```
  ┌─────────────────────────────────────────┐
  │    Послідовний обхід 15 ігор            │
  └──────────────────┬──────────────────────┘
                     │
                     ▼
  ┌─────────────────────────────────────────┐
  │     Запит до Steam Web API              │
  │     (ліміт відповіді: 10 000 записів)   │
  └──────────────────┬──────────────────────┘
                     │
          ┌──────────▼──────────┐
          │  Отримано 10 000?   │
          └──────┬──────┬───────┘
             ТАК │      │ НІ
                 ▼      ▼
  ┌──────────────────┐ ┌─────────────────────┐
  │ Субфільтри за    │ │ Результат повний    │
  │ регіоном та      │ └──────────┬──────────┘
  │ гравцями.        │            │
  │ Пауза 1 с.       │            │
  │ Дедублікація.    │            │
  └────────┬─────────┘            │
           └──────────────┬───────┘
                          ▼
  ┌─────────────────────────────────────────┐
  │  Збереження результатів                 │
  │  1. Нормалізація полів серверів         │
  │  2. Upsert партіями по 500 записів      │
  │  3. Запис онлайну в online_records      │
  └─────────────────────────────────────────┘
```

Збереження реалізоване через атомарну операцію вставки з обробкою конфліктів: якщо сервер із таким самим IP та портом уже існує — він оновлюється, інакше — додається. Це виключає ризик стану конкурентного доступу, який виникав би при класичному підході «перевірка — вставка» (два окремих запити до бази). Обробка партіями по 500 записів запобігає надмірному блокуванню таблиці при масивах понад двадцять п'ять тисяч серверів. Кожен запуск задачі збору генерує від 500 000 до 600 000 нових рядків у таблиці записів онлайну.

Система журналювання побудована на бібліотеці winston. Усі події одночасно виводяться в консоль і записуються у щоденні файли журналу з автоматичною ротацією. Кожен запуск задачі фіксує час початку, проміжний прогрес та загальний час виконання; помилки зберігаються з повним стеком викликів.

## 3.2 Реалізація REST API бекенду

Серверний застосунок реалізований на фреймворку NestJS та відповідає виключно за читання, фільтрацію і трансформацію вже зібраних даних з PostgreSQL. Застосунок складається з двох модулів: модуль ігор обробляє запити до каталогу ігор, модуль серверів — запити щодо серверів та аналітики. Кожен модуль містить контролер (маршрутизація та валідація параметрів) і сервіс (бізнес-логіка та запити до бази). Інтерактивна Swagger-документація доступна за адресою `/api/docs`.

Ключовим ендпоінтом є отримання пагінованого списку серверів із підтримкою фільтрів. У таблиці 3.2 наведено параметри цього запиту.

**Таблиця 3.2 — Параметри запиту до ендпоінту списку серверів**

| Параметр  | Призначення                                                            |
|-----------|------------------------------------------------------------------------|
| appid     | Ідентифікатор гри в Steam (обов'язковий)                               |
| search    | Підрядковий пошук у назві сервера                                      |
| ip        | Точний збіг IP-адреси                                                  |
| map       | Точний збіг назви карти                                                |
| isSecure  | Фільтр за наявністю VAC-захисту                                        |
| isOnline  | Фільтр за поточним статусом доступності                                |
| sortBy    | Поле сортування: рейтинг / гравці / назва                              |
| sortOrder | Напрямок: за зростанням або спаданням                                  |
| page      | Номер сторінки (за замовчуванням: 1)                                   |
| limit     | Кількість записів на сторінку, не більше 100 (за замовчуванням: 25)    |

Відповідь містить масив серверів поточної сторінки, загальну кількість записів і метадані пагінації. До кожного сервера автоматично приєднуються показники популярності та стабільності з таблиці рейтингів. При сортуванні за рейтингом сервери без присвоєного рангу виводяться в кінці списку.

## 3.3 Реалізація системи аналітики та графіків

Система аналітики реалізована через чотири типи часових рядів, кожен з яких відповідає окремому ендпоінту бекенду. Підтримуються діапазони 24 години, 3, 7 та 30 днів. Графік динаміки онлайну сервера за 24-годинний діапазон формує 96 точок із кроком 15 хвилин; для ширших діапазонів — погодинний крок, оскільки старіші записи вже агреговані. Графік рейтингу та балу будується з таблиці щоденних рейтингів і доступний лише від 3 до 30 днів. Графік uptime за 24 години обчислюється безпосередньо з таблиці записів онлайну, а для ширших діапазонів — зі щоденних рейтингів. Статистика онлайну гри зчитується з денормалізованого JSONB-поля без додаткових з'єднань.

Основна складність полягає в можливій відсутності даних за окремі проміжки: при звичайній вибірці рядків графік матиме пропуски. Вирішенням є використання функції генерації рівномірних часових рядів PostgreSQL: вона повертає повний перелік часових слотів, до яких реальні дані приєднуються зовнішнім з'єднанням, а відсутні значення замінюються нулем. На рисунку 3.2 зображено цей принцип трансформації.

**Рисунок 3.2 — Формування часового ряду з заповненням пропусків**

```
  Згенеровані слоти (крок 15 хвилин):
  [ 10:00 | 10:15 | 10:30 | 10:45 ]

  Зовнішнє з'єднання з таблицею онлайну:
  [ 42    |  —    |  —    |  37   ]
              ↓      ↓
  Заміна відсутніх значень нулем:
  [ 42    |  0    |  0    |  37   ]

  Результат: завжди рівно N точок незалежно від наявності даних
```

## 3.4 Приклад використання системи

Розглянемо типовий сценарій пошуку ігрового сервера. Користувач відкриває сторінку обраної гри, де відображається поточний сумарний онлайн і графік погодинної активності — ці дані зчитуються миттєво з денормалізованого поля в таблиці ігор. Далі він переходить до списку серверів, відсортованого за рейтингом за замовчуванням, та застосовує фільтри за назвою, картою та VAC-захистом. Відкривши сторінку обраного сервера, користувач переглядає три аналітичних графіки: динаміку онлайну, зміну рейтингу та рівень доступності — кожен з яких формується із заповненням пропусків і завжди містить фіксовану кількість точок.

Паралельно система безперервно виконує фонові задачі. За типову добу задача збору запускається дев'яносто шість разів і формує понад 50 мільйонів нових записів онлайну, задача рейтингів створює близько 600 000 щоденних знімків, а задача очищення обробляє понад мільйон записів, агрегуючи деталізовані дані до погодинних і видаляючи записи, що перевищують 30-денний горизонт зберігання.
