## 3.1 Реалізація системи збору статистики

Worker-сервіс є центральним компонентом платформи Serverscope, відповідальним за збір, обробку та збереження всієї статистики. Він реалізований як автономний фоновий процес на Node.js з TypeScript з чотирма автоматизованими планованими задачами. Worker не має зовнішнього HTTP-інтерфейсу і взаємодіє виключно з базою даних PostgreSQL через бібліотеку TypeORM.

### 3.1.1 Структура проекту

Проект побудований за принципом розподілу обов'язків: кожен модуль виконує одну чітко визначену функцію і не виходить за її межі. Таблиця 3.1 описує призначення кожного компонента проекту.

**Таблиця 3.1 — Структура файлів Worker-сервісу**

|--------------------------------|-----------------------------------------------------------------------------|

### 3.1.2 Ініціалізація та запуск

При запуску Worker виконує послідовну процедуру ініціалізації. Першим кроком встановлюється з'єднання з базою даних PostgreSQL. Лише після успішного підключення реєструються чотири планованих задачі. Якщо підключення до бази даних не вдалося — процес завершується примусово, що дозволяє системному менеджеру (наприклад, Docker або PM2) автоматично перезапустити сервіс.

### 3.1.3 Алгоритм задачі збору серверів

Задача збору серверів є найбільш складною за логікою виконання. Вона послідовно обробляє всі 15 ігор зі списку відстежуваних: для кожної гри виконується запит до Steam Web API, отримані дані нормалізуються та зберігаються в базі. Особливість полягає в обробці ліміту Steam API — якщо відповідь містить рівно 10 000 серверів, це свідчить про досягнення максимуму, і реальна кількість серверів може бути більшою. У такому разі запит розбивається на серію вужчих запитів із субфільтрами за регіоном або кількістю гравців.

На рисунку 3.1 наведено алгоритм виконання задачі збору серверів.

### 3.1.4 Механізм збереження серверів

Після отримання даних з Steam API обробка виконується партіями по 500 записів. Такий підхід запобігає перевантаженню бази даних при великих масивах — для деяких ігор кількість серверів перевищує 25 000 за один запит.

Збереження кожного сервера реалізовано через операцію вставки з обробкою конфліктів: якщо в базі вже існує запис із таким самим IP та портом опитування — він оновлюється, в іншому разі — додається новий. Перевага цього підходу перед класичним варіантом "перевірка — вставка" (два окремі запити) полягає в атомарності: операція виконується єдиним запитом без ризику виникнення стану конкурентного доступу. Порівняння підходів наведено в таблиці 3.3.

**Таблиця 3.3 — Порівняння підходів до збереження серверів**

| Критерій                   | Два окремі запити (перевірка + вставка) | Атомарна вставка з обробкою конфліктів |
|----------------------------|-----------------------------------------|----------------------------------------|
| Кількість запитів до БД    | 2 (SELECT + INSERT або UPDATE)          | 1 атомарний запит                      |
| Ризик конкурентного доступу| Наявний (між перевіркою та вставкою)    | Відсутній (атомарна операція)          |
| Продуктивність             | Нижча (подвійне навантаження)           | Вища (один зворотний виклик до БД)     |
| Складність реалізації      | Вища (умовна логіка перевірки)          | Нижча (декларативний підхід)           |
| Придатність для партій     | Ускладнена                              | Проста (передається масив сутностей)   |

Паралельно зі збереженням стану серверів виконується запис поточного онлайну до таблиці `online_records`. Кожен запуск задачі збору генерує до 600 000 нових рядків у цій таблиці.

### 3.1.5 Система журналювання

Worker використовує власний модуль журналювання на базі бібліотеки winston. Усі події — інформаційні повідомлення, попередження та помилки — одночасно виводяться до консолі та зберігаються у файлах щоденного журналу. Файли формуються автоматично за датою та зберігаються у директорії logs. На рисунку 3.2 зображено схему маршрутизації журнальних записів.

**Рисунок 3.2 — Схема журналювання Worker-сервісу**

```
  Подія (інформаційне повідомлення / попередження / помилка)
                          │
                          ▼
                 ┌────────────────┐
                 │   Модуль       │
                 │ журналювання   │
                 │   (winston)    │
                 └───────┬────────┘
                         │
             ┌───────────┴───────────┐
             ▼                       ▼
      Виведення в консоль     Запис у файл
                              logs/2026-05-28.log
                              logs/2026-05-29.log
                              (нові файли щодня)
```

Кожен запуск планованої задачі фіксує час початку, проміжний прогрес (наприклад, кількість збережених записів) та загальний час виконання. У разі виникнення помилки зберігається повний стек викликів, що дозволяє ретроспективно діагностувати збої та відстежувати продуктивність задач у часі.

## 3.2 Реалізація REST API бекенду

Серверний застосунок (бекенд) реалізований на фреймворку NestJS і відповідає за надання даних клієнтам через REST API. Він не виконує жодних звернень до Steam API і не містить бізнес-логіки збору — його єдиним обов'язком є читання, фільтрація та трансформація вже зібраних даних з PostgreSQL.

### 3.2.1 Архітектура та модулі

NestJS використовує модульну архітектуру: кожен предметний домен (ігри, сервери) оформлений як окремий самостійний модуль з контролером, сервісом та сутностями. Контролер відповідає за маршрутизацію запитів, сервіс — за бізнес-логіку та звернення до бази даних. Таблиця 3.4 описує модулі бекенду та їх відповідальність.

**Таблиця 3.4 — Модулі серверного застосунку**

| Модуль        | Обов'язок контролера             | Обов'язок сервісу                                        | Ендпоінти                                       |
|---------------|----------------------------------|----------------------------------------------------------|-------------------------------------------------|
| Ігри          | Маршрутизація запитів про ігри   | Пошук, пагінація, читання погодинного онлайну           | Список ігор, деталі гри за ідентифікатором      |
| Сервери       | Маршрутизація запитів про сервери| Фільтрація, пагінація, побудова графіків, деталі сервера | Список серверів, деталі, графіки онлайну/рейтингу/uptime |

Інтерактивна документація API автоматично генерується на основі анотацій у вихідному коді та доступна за адресою `/api/docs` у вигляді Swagger UI. На рисунку 3.3 зображено структуру файлів серверного застосунку.

**Рисунок 3.3 — Структура файлів серверного застосунку**

```
  ├── games/
  │   ├── games.module.ts
  │   ├── games.controller.ts   ← маршрутизація запитів
  │   ├── games.service.ts      ← запити до БД, логіка
  │   ├── games.entity.ts       ← опис таблиці games
  │   └── dto/                  ← схеми запитів і відповідей

      ├── servers.service.ts    ← запити до БД, логіка
      ├── servers.entity.ts     ← опис таблиці servers
      ├── server-ranking.entity.ts
      ├── online-record.entity.ts
      └── dto/                  ← схеми запитів і відповідей
```

### 3.2.2 Ендпоінти та параметри запиту

Ключовим ендпоінтом платформи є отримання списку серверів, який підтримує повний набір параметрів фільтрації та пагінації. Таблиця 3.5 наводить усі доступні параметри запиту.

**Таблиця 3.5 — Параметри запиту до ендпоінту списку серверів**

| Параметр       | Тип      | Обов'язковий | Опис                                                            |
|----------------|----------|--------------|-----------------------------------------------------------------|
| appid          | число    | Так          | Ідентифікатор гри в Steam                                       |
| search         | рядок    | Ні           | Підрядковий пошук у назві сервера (без врахування регістру)     |
| ip             | рядок    | Ні           | Точний збіг IP-адреси                                           |
| map            | рядок    | Ні           | Точний збіг назви карти                                         |
| isSecure       | булеве   | Ні           | Фільтр за наявністю античит-захисту VAC                         |
| isOnline       | булеве   | Ні           | Фільтр за поточним статусом доступності сервера                 |
| sortBy         | перелік  | Ні           | Поле сортування: рейтинг / гравці / назва (за замовч.: рейтинг) |

Відповідь ендпоінту містить масив серверів поточної сторінки, загальну кількість знайдених записів, а також поточну сторінку, обраний ліміт і загальну кількість сторінок. До кожного сервера автоматично приєднуються показники популярності та стабільності з найостаннішого запису в таблиці рейтингів. При сортуванні за рейтингом сервери без присвоєного рангу автоматично виводяться останніми незалежно від інших умов сортування.

## 3.3 Реалізація системи аналітики та графіків

Система аналітики реалізована через чотири типи часових рядів, кожен з яких відповідає окремому ендпоінту бекенду. Ключова технічна особливість підсистеми — формування повної часової осі з гарантованою кількістю точок незалежно від наявності або відсутності реальних даних за окремі проміжки часу.

### 3.3.1 Огляд ендпоінтів графіків

Система підтримує чотири періоди аналізу: 24 години, 3 дні, 7 днів та 30 днів. Залежно від обраного періоду змінюється крок часової осі та джерело даних — це дозволяє зберігати прийнятний рівень деталізації без надмірного навантаження на базу. Характеристики кожного типу графіку наведено в таблиці 3.6.

**Таблиця 3.6 — Характеристики ендпоінтів графіків**

| Тип графіку       | Ендпоінт                        | Джерело даних                        | Крок (24 год) | Крок (3/7/30 дн.) | Точок за 7 днів |
|-------------------|---------------------------------|--------------------------------------|---------------|-------------------|-----------------|
| Онлайн сервера    | /servers/:id/chart              | Таблиця записів онлайну              | 15 хвилин     | 1 година          | 168             |
| Рейтинг / Бал     | /servers/:id/rank-chart         | Таблиця рейтингів                    | —             | 1 доба            | 7               |
| Uptime            | /servers/:id/uptime-chart       | Записи онлайну / таблиця рейтингів   | 1 година      | 1 доба            | 7               |
| Онлайн гри        | /games/:appid                   | Поле погодинного кешу в таблиці ігор | 1 година      | —                 | 24              |

Для графіка рейтингу доступні лише діапазони від 3 до 30 днів, оскільки рейтинги розраховуються один раз на добу і 24-годинна деталізація є недоцільною.

### 3.3.2 Формування повної часової осі

Основна складність при побудові графіків полягає в можливій відсутності даних за окремі проміжки часу: сервер міг бути тимчасово недоступний, або цикл збору міг завершитися з помилкою. При звичайній вибірці рядків за діапазоном дат результуючий графік матиме пропуски — різну кількість точок для різних серверів.

Вирішення: база даних PostgreSQL надає функцію генерації рівномірних часових рядів, що дозволяє отримати повний перелік часових слотів для заданого діапазону та кроку. Далі реальні дані приєднуються до цих слотів зовнішнім з'єднанням, а відсутні значення замінюються нулем. Таким чином, відповідь завжди містить рівно стільки точок, скільки слотів у вибраному діапазоні. На рисунку 3.5 зображено цей принцип трансформації.

**Рисунок 3.5 — Формування часового ряду з заповненням пропусків**

```
  Часові слоти (згенеровані, по 15 хв):
  ┌──────────┬──────────┬──────────┬──────────┐
  │  10:00   │  10:15   │  10:30   │  10:45   │
  └────┬─────┴────┬─────┴────┬─────┴────┬─────┘
       │          │          │          │
       │ Зовнішнє з'єднання з таблицею онлайну
       │          │          │          │
       ▼          ▼          ▼          ▼
  ┌──────────┬──────────┬──────────┬──────────┐
  │  42 грав.│  (немає) │  (немає) │  37 грав.│
  │  (запис  │  → 0     │  → 0     │  (запис  │
  │   є)     │          │          │   є)     │
  └──────────┴──────────┴──────────┴──────────┘
       │          │          │          │
       ▼          ▼          ▼          ▼
  Результат: [{10:00, 42}, {10:15, 0}, {10:30, 0}, {10:45, 37}]
```

Для графіка за 24 години формується 96 слотів із кроком 15 хвилин. Для діапазонів від 3 до 30 днів — погодинні слоти. Це відповідає моделі зберігання даних: деталізовані 15-хвилинні записи зберігаються лише за останні 24 години, а старіші агрегуються до погодинних.

### 3.3.3 Реалізація кожного типу графіку

**Графік онлайну сервера.** Для 24-годинного діапазону формуються 96 слотів з 15-хвилинним кроком. Для ширших діапазонів (3, 7, 30 днів) — погодинні слоти. В обох випадках для кожного слоту обчислюється середнє значення кількості гравців серед усіх записів, що потрапили в цей часовий інтервал, а за відсутності записів підставляється нуль.

**Графік рейтингу та балу.** Дані надходять із таблиці щоденних рейтингів. Для кожної доби в заданому діапазоні вибирається найактуальніший запис. Відповідь містить три паралельні числові ряди: числовий ранг, рейтинговий бал та коефіцієнт uptime.

**Графік uptime.** Для 24-годинного діапазону рівень доступності сервера за кожну годину обчислюється безпосередньо з таблиці записів онлайну: підраховується кількість записів за годину та ділиться на чотири (максимально можлива кількість записів при 15-хвилинному кроці). Для ширших діапазонів використовується готовий коефіцієнт доступності зі щоденних рейтингів.

**Графік онлайну гри.** Не потребує додаткового звернення до таблиці записів онлайну: в таблиці ігор зберігається спеціальне поле у форматі JSONB з масивом із 24 значень, що містить середній онлайн за кожну з останніх 24 годин. Це поле щогодини оновлюється задачею агрегування і зчитується миттєво — без виконання складних з'єднань таблиць.

Деталізована характеристика реалізації кожного типу графіку наведена в таблиці 3.7.

**Таблиця 3.7 — Деталізація реалізації графіків**

| Тип графіку   | Діапазон  | Спосіб формування слотів            | Кількість точок | Заповнення пропусків                  |
|---------------|-----------|-------------------------------------|-----------------|---------------------------------------|
| Онлайн        | 24 год    | Часовий ряд з кроком 15 хвилин      | 96              | Нуль (середнє без записів)            |
| Онлайн        | 3 / 7 дн. | Часовий ряд з погодинним кроком     | 72 / 168        | Нуль (середнє без записів)            |
